# ミセルダケ 技術仕様書（開発者ハンドオフ用）

対象：本人確認書類・個人情報を含む画像の自動マスキング（黒塗り／モザイク）アプリ
方針：サーバーに画像を送らない／アカウント登録不要／フリーミアム（透かし解除で買い切り）

---

## 1. プロダクト概要

| 項目 | 内容 |
|---|---|
| アプリ名（仮） | ミセルダケ |
| タグライン | 必要な情報だけ、見せる。 |
| 解決する問題 | フリマ取引・単発バイト・賃貸契約などで身分証の写真を送る際、住所・生年月日・マイナンバー等の不要な情報まで晒してしまう |
| コアUX | ①撮影 or 選択 → ②AIが個人情報らしき領域を自動検出しマスキング候補を提示 → ③タップで調整・確定 → ④透かし入りは無料書き出し／透かし解除は買い切り課金 |
| ターゲット | フリマ・個人間取引の利用者、単発バイト・ギグワーカー、賃貸契約時の入居者 |
| 非搭載機能 | 本人確認そのもの（eKYC）、書類の真正性検証、クラウド保管・共有機能 |

## 2. 市場・差別化についての正直な注記

2025年6月、Appleは**iPhone Wallet上でマイナンバーカードを提示する際、どの情報が相手に共有されるか事前に確認・選択できる機能**を提供開始した（[Apple公式](https://www.apple.com/jp/newsroom/2025/06/apple-introduces-my-number-card-on-iphone/)）。これは「デジタル提示（NFC/QR）」の文脈でのマスキングであり、**本アプリが狙う「紙・カードを撮影してJPEG/PDFとして第三者にアップロード・送付する」用途とは重ならない**。フリマ・単発バイト・賃貸等、いまだに「画像アップロード」を求めるサービスが大半である限り、この用途のギャップは残る。ただし将来的にeKYC事業者側がAppleのデジタル提示に対応していくと、中長期的に市場が縮小するリスクは認識しておく（[参考](https://www.cybertrust.co.jp/blog/certificate-authority/business-process-digitalization/applewallet-my-number.html)）。

## 3. MVPスコープ

### 含める
- 撮影 or カメラロールから選択（1枚ずつ、まずは静止画のみ）
- オンデバイスでの個人情報領域の自動検出（住所・生年月日・個人番号・QRコード等のテキスト/コード領域）
- 検出領域のプレビュー表示＋タップで対象追加・解除、ドラッグでマスク範囲の手動調整
- 黒塗り／モザイクの2種類のマスキングスタイル
- 書き出し（無料版は右下に控えめな透かし、購入で透かし解除）
- 書類種別プリセット（運転免許証／マイナンバーカード／保険証／パスポート／その他自由選択）→ プリセットは「よく隠す項目」の初期候補を出すだけで、最終判断は必ずユーザー確認を挟む

### 含めない（v1では）
- 複数枚一括処理・PDF出力（v1.1以降で検討）
- クラウド同期・共有リンク発行（プライバシー訴求と矛盾するため不採用）
- 書類の真正性チェック・OCRでの氏名等の読み取り表示（読み取り精度の誤解を招くリスクを避け、「領域検出」に留める）
- アカウント・ログイン機能

## 4. アーキテクチャ概要

```
┌─────────────────────────────┐
│         クライアントのみ           │
│  (iOS App / Android App)     │
│                               │
│  - オンデバイス画像処理          │
│    (Vision / ML Kit)          │
│  - ローカルの一時ファイルのみ     │
│    (書き出し後は即破棄可)        │
│  - StoreKit / Billing         │
│    (透かし解除の買い切り課金)    │
└─────────────────────────────┘
        │ 通信なし（オフラインで完結）
        ▼
      （サーバーなし）
```

**設計原則：画像は端末外に一切送信しない。** これはコスト削減だけでなく、「本人確認書類をクラウドに送りたくない」という心理的抵抗が最も強いカテゴリだからこそ、最大の差別化・訴求ポイントになる。

## 5. iOS 実装（Swift / SwiftUI）

| 機能 | 実装方法 | 留意点 |
|---|---|---|
| テキスト/個人情報領域の検出 | `Vision`（`VNRecognizeTextRequest`）でテキスト領域を検出し、生年月日・数字列（12桁のマイナンバー等）のパターンにマッチする領域を候補として優先表示 | 内容の意味解釈はせず「検出→候補提示→人間が最終確認」に徹する（誤検出時の責任をユーザー確認で担保） |
| QRコード領域の検出 | `VNDetectBarcodesRequest` | マイナンバーカードのQR/バーコード欄を自動候補に含める |
| マスキング描画 | `Core Graphics`でマスク画像を合成し書き出し | 元画像はEXIF情報（位置情報等）を書き出し時に除去 |
| 透かし | 無料時は`CIFilter`等で書き出し画像に半透明ロゴを合成 | 課金後は`StoreKit 2`のトランザクション確認後にウォーターマークなし書き出しへ切替 |
| 課金 | `StoreKit 2`、非消費型（Non-Consumable）で買い切り実装 | レシート検証はローカルの`Transaction.currentEntitlements`で完結、サーバー不要 |
| ローカル処理のみの担保 | ネットワーク権限を極力使わない設計にし、Info.plistでの通信要求を最小化 | 審査説明・プライバシーラベルで「データ収集なし」を明記できる設計にする |

## 6. Android 実装（Kotlin）

| 機能 | 実装方法 | 留意点 |
|---|---|---|
| テキスト領域の検出 | `ML Kit Text Recognition`（オンデバイスモデル） | 完全オフライン動作モデルを明示的に指定（クラウドAPI版を誤って使わない） |
| バーコード/QR検出 | `ML Kit Barcode Scanning` | — |
| マスキング描画 | `Canvas`合成、`Bitmap`書き出し | EXIF除去を`ExifInterface`で実施 |
| 課金 | `Google Play Billing Library`、買い切り（one-time product） | — |
| ローカル処理のみの担保 | ネットワークパーミッション自体を最小化 | Data Safetyフォームで「データ収集なし」を選択できる構成に |

---

## 7. プライバシー・データ設計

- 画像・処理結果ともに**端末外へ送信しない**（サーバー通信なし）
- 処理用の一時ファイルはアプリのサンドボックス内にのみ保持し、書き出し完了後はキャッシュを自動クリア
- 位置情報・連絡先などの権限は一切要求しない
- アカウント登録・氏名/メール/電話番号の収集なし
- プライバシーポリシーで「本アプリは画像を外部送信しません」と明記し、ストア審査・レビューでの信頼獲得に直結させる

## 8. マネタイズ（フリーミアム／透かし解除）

| 項目 | 内容 |
|---|---|
| 無料版 | 検出・マスキング機能はフル利用可。書き出し画像の右下に控えめな透かしロゴが入る |
| 有料版 | 買い切り課金（非消費型）で透かし解除。¥500程度を想定 |
| 買い切りにする理由 | 利用頻度が低い（数ヶ月〜年に数回）ユーザーが多く、サブスクにする合理性がない。都度の価値が明確なので一度の購入で心理的抵抗が小さい |
| 将来の追加課金候補 | 書類種別プリセットの拡張パック、複数枚一括処理（v1.1以降）。ただし継続課金は導入しない方針を維持 |
| 損益分岐点の考え方 | サーバー費用ゼロのため、ストア手数料控除後の売上がそのまま開発工数の回収に充当される。数百本の販売で黒字化する設計 |

## 9. 画面一覧・画面遷移（MVP）

1. ホーム（撮影 / カメラロールから選択）
2. 書類種別選択（任意・スキップ可）
3. 検出結果プレビュー（候補領域のON/OFF、手動調整）
4. マスキングスタイル選択（黒塗り／モザイク）
5. 書き出しプレビュー（透かしの有無を明示）→ 保存 or 購入導線
6. 購入画面（StoreKit/Billingの標準UI）

初回起動から「①撮影→②候補確認→③書き出し」までを30秒以内で完了できることを目標にする。

## 11. 最大のリスク（正直な評価）

- 個人情報領域の検出精度が不十分だと「隠したつもりが隠れていなかった」という致命的な失敗につながる。**必ず人間の最終確認ステップを挟む設計を外さないこと。**
- Apple Walletのマイナンバーカード選択的開示機能が拡大すると、少なくとも行政手続き文脈での需要は緩やかに縮小する可能性がある（本書2章参照）
- 「本人確認書類の加工」というカテゴリ自体が、悪用（偽装書類作成への転用等）を疑われやすく、ストア審査説明・スクリーンショットで「提出用の安全な共有を助けるツールである」ことを明確に訴求する必要がある
